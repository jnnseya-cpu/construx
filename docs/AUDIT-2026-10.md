# CONSTRUX end-to-end audit — October 2026

A whole-platform review and test, from the chair of a **real client who has no
access to the AI assistant** — the lens being "can an unaided user actually
complete what the product invites them to do, without a dead-end, a fake
figure, or an error they can't act on."

Scope: ~100 domain modules, 14 engines, ~60 frontend pages, 1,277 routes. Two
passes: **Pass A** drove the real HTTP gateway in-process as a logged-in user;
**Pass B** ran deep per-area code+UX reviews, each tracing capabilities end to
end (frontend → route → domain → ledger → UI) and reporting only verified,
evidence-backed findings.

Severity: **P0** platform/money failure · **P1** critical feature unusable ·
**P2** functional defect · **P3** improvement · **P4** cosmetic.

> **Remediation status (updated as work lands).** The systemic P1 — the missing
> write-UI across stage workflows — has now been **closed for the reviewed
> workflows**, each with a gateway journey test that drives the exact payloads
> the buttons send and asserts the flow completes: submittals, design
> change/baseline, concept stage (gate opens), construction progress +
> deliveries + commissioning dossier, handover acceptance spine, meeting-action
> close, and project-invitation accept/decline. Security/correctness/honesty
> fixes from the audit are also applied (see "Fixes applied"). The frontend
> quick-wins are now applied too: economy "0 ACU" field map, account
> blank-on-error, permissions label drift, portfolio "AM" region, estate
> module-gate heading, billing "Issue invoice" relabel, commercial double-dialog,
> the duplicate procurement clarification command key, and the field.js
> site-capture dead-end. The two backend P2s are now **fixed**: award-departures
> (submitted commercial terms are captured at submission so a moved date or
> changed LD rate is detected at award) and the conditional-handover-acceptance
> lapse (operations are refused off an acceptance whose condition has passed its
> expiry). The handover **requirements-matrix** sub-workflow is **built**, and so
> now is `defineHandoverSection` (sectional handover) — the "multiselect"
> affordance it needed is a one-reference-per-line textarea, the same pattern the
> rest of the console uses, with the server refusing any reference outside the
> matrix. The autopilot **§16.1 disclosure on "Approve and run"** is now **done**
> too: the approve flow quotes the command's own engine route through the existing
> `confirmCost`/`/v1/ai/quote` path and shows the cost and the transmission
> disclosure before committing — no proposal→command→quote wiring was needed
> because each command maps to its AI route directly. Closing it surfaced and
> fixed a 500 in the same handler (two fleet-raised commands had no dispatcher in
> `AGENT_COMMANDS`). Nothing from this audit now remains open.

## Pass A — real-user HTTP sweeps (executed, not read)

Booted `createGateway(platform)` in-process, seeded a tenant, logged in as the
enterprise owner, and exercised the real pipeline (validation → authz →
problem+json).

- **Read surface (275 GET screens reached): 0 broken (5xx), 0 fake-data hits.**
  Every parameterless/project screen a logged-in user can open renders. No
  white-screen-of-death.
- **Write surface (463 POST/PUT hit with an empty body): 0 crashes (5xx).** A
  fumbled/empty form returns a clean, actionable `400 VALIDATION_FAILED`
  (problem+json), never a 500. Verified in isolation on representative tenant
  writes (`/v1/projects`, daily-logs).
- **Refusals are clean and actionable.** The owner's 68 read denials are the
  correct tenant-vs-operator boundary (`PLATFORM_ADMIN_REQUIRED` for `/v1/admin/*`,
  `MODULE_NOT_GRANTED` for `/v1/bid-on/*`) — well-worded problem+json, not walls.
- **`/v1/documents/lifecycle/:projectId` 404** was a sweep param mismatch, not a
  dead-end: the route is `:id` = *document* id, tenant-scoped; the frontend only
  ever calls it with a real document id. Cleared.
- The apparent "453 writes → 401" in the bulk write-sweep was **self-inflicted**:
  the loop hit `POST /v1/auth/logout` partway through, which revoked the session
  token, so every later call 401'd (`"Token has been revoked"`). Not a defect.

**Pass A verdict: the platform's HTTP surface is robust — it loads, it validates,
it refuses cleanly, and it does not crash or show fake numbers on reads.** What
Pass A cannot see is whether a *multi-step journey completes* — that is Pass B.

## Pass B — deep per-area reviews

Twelve areas, one reviewer each. **All 12 complete.** Each traced its
capabilities end to end and reported only verified, evidence-backed findings.

### Systemic pattern (the headline)

Across the two areas reviewed so far that are *stage workflows* (Concept and
Design), the same defect recurs and it is the one that matters most to an
unaided client: **the backend is complete and the screen is a rich read
surface, but the write commands that move the stage forward were never wired
into the UI.** The client can see everything and complete almost nothing past
"create". This is the Bid-On pattern (read-complete, write-affordances-missing)
at platform scale, and it is the primary thing standing between CONSTRUX and
"a client can use it without the assistant."

## The headline: one systemic defect, many instances

The single most important finding, repeated in **every stage-workflow area**
(concept, design, submittals, construction progress + delivery, commissioning,
handover, completion, aftercare, meetings, invitations): **the backends are
complete and the screens are rich read surfaces, but the write commands that
move a workflow forward were never wired into the UI.** A client can watch state
and create initial records, but cannot drive a project to completion — the stage
freezes, the register only grows, the "next command" is printed with no button.

This is the Bid-On pattern (read-complete, write-affordances-missing) at platform
scale, and it is the thing standing between CONSTRUX and "a client can use it
without the assistant." It is not a backend defect and not a security defect —
it is an **unfinished UI vertical presented as finished** (rule 8 / rule 9), and
it is largely **not disclosed in STATE.md's "what is not built"**.

The affected write journeys, each needing command specs + panel affordances wired
the way Bid-On's and `design.js`'s existing commands are:

| Area | Missing write journey |
|---|---|
| Concept | analyse/select option, create cost-plan, programme, cashflow, approve controls, 3 strategies, compliance screen, risk review, due-diligence, brief baseline, freeze concept baseline |
| Design | raise→**submit** submittal, resubmit, record-ordered; raise/assess/decide/implement/close design-change; freeze package; approve baseline; MIDP |
| Construction | set measurement-basis / submit progress-claim / verify; goods-in book/receive/accept/install |
| Commissioning | compile dossier; complete commissioning |
| Handover | compile pack, decide, activate operations, baseline, transfer residuals, requirements matrix |
| Completion | release turnover, accept construction completion, practical-completion inspection/certificate |
| Aftercare | start, seasonal commissioning, feedback; operator-readiness acceptance; regulatory pack approve/submit |
| Meetings | close action; record correction |
| Onboarding | **accept/decline a project invitation** |

## Fixes applied in this audit

Verified, typechecked, and covered by the full suite (7,800+ tests) plus the
noted targeted tests. Each mirrors a pattern already tested elsewhere in the
codebase.

- **Bid-On customer-guest dead-end (P1)** — classified the two bootstrap reads
  `guest: 'OWN'` so the external guest's screen loads (`routes.ts`).
- **Competitor-pricing cross-project leak (P2/security)** — `tenderintel.ts`
  `requireComparison` now scopes by tenant + project.
- **RFQ-reconcile cross-project leak (P3)** — `procurement.ts` scopes the RFQ.
- **Site-model cross-project read (P3)** — `sitemodel.ts` `requireModel` scopes by
  project, matching `heldIfc`.
- **Structural parent-scope gaps (P3)** — `structure.ts` validates `createPortfolio`'s
  enterprise and tenant-checks `createProject`/`createProgramme`'s parent portfolio.
- **Audit-timeline honesty (P2)** — a withdrawn direction now emits a new
  `DIRECTION_WITHDRAWN` event type instead of `DIRECTION_CONFIRMED`, so the Golden
  Thread no longer narrates "confirmed" for a withdrawal (`eventTypes.ts`,
  `informationcontrol.ts`; catalogue test added).
- **Autopilot approval 500 (P2)** — the approve route dispatches a proposal's
  command through a hand-written table that was missing two commands the fleet
  actually raises (`cdm:draftToolboxTalk`, `tenderintake:extractRequirements`).
  Approving one wrote the approval and then threw `No dispatcher` as a 500, leaving
  the proposal APPROVED-but-never-run and the approver staring at a server error —
  exactly the dead-end an unaided client cannot pass. Both dispatchers added, each
  running as the approver through the same engine path a manual call takes
  (`routes.ts` `AGENT_COMMANDS`; `autopilotapproval.test.ts` approves the toolbox-talk
  proposal over HTTP in the CONSTRUCTION-phase seed project and asserts it executes).
- **Autopilot §16.1 disclosure on approval (P2)** — approving a proposal whose
  command reaches an AI provider spends from the wallet and transmits project data,
  and the queue committed it with no cost shown and no data-transmission notice. The
  screen now prices and discloses it first: for the four AI-reaching commands it
  quotes the engine route through the same `confirmCost`/`/v1/ai/quote` path every
  manual AI action uses, and only approves if the person accepts (`autopilot.js`;
  same test quotes all four paths over HTTP and asserts the §16.1 disclosure is
  present, and that quoting spends nothing).
- **Pipeline screen crash on an unread tender file (P1)** — opening Pipeline &
  Bid Decisions on a worked TENDER project threw `Cannot read properties of
  undefined (reading 'kind')` and blanked the whole page. The reader table reads
  each held file's classification `kind`; a held file that has never been
  ingested carries no ingestion record and so no `file` at all —
  `heldTenderFiles` returns it as the UNREAD "look at the file first" road with
  the entry alone. The render read `file.kind` before the road was known, so any
  tender pack containing an uploaded-but-not-yet-read document (the spec, a
  schedule, an addendum) crashed the screen for everyone on that project. Fixed by
  guarding the leading read (`file && String(file.kind ?? '')`) so an UNREAD row
  falls through to its own branch, which the file-less row was always meant to
  reach (`pipeline.js`; `ingestion.test.ts` locks the data contract — a held file
  off the ingestion list — and the fix was reproduced over the real backend
  before and after).

- **Tender document un-filable against a second project (P1)** — a tender pack
  filed against one project could not be filed against another, and the second
  project was left permanently empty with no recovery path. `recordTenderDocument`
  deduped with the tenant-wide `findByHash`, but `EvidenceItem` records are
  project-scoped and the store keys bytes by hash at the tenant level — so the
  same drawings going out on two lots hit `EVIDENCE_ALREADY_FILED` on the second
  project, which then showed "0 drawings filed" while every upload was refused as
  "already filed", with no UI affordance to attach an on-record document to the
  current project. Fixed by scoping the tender-document duplicate check to the
  project: a new `findByHashInProject` (registry.ts) asks "is this file already on
  *this* project's register" instead of "does this tenancy own it", so each
  project gets its own record over the one shared blob (`tenderintake.ts`
  `recordTenderDocument`). The tenant-wide `findByHash` is untouched and still
  guards genuine company facts (insurance certs, test results, evidence claims,
  signing, BIM/perception, the orphan-discard refusal, the byte-upload target) —
  every other caller was checked and none changed behaviour. The genuine
  protection is kept: the same file filed twice *on one project* is still refused.
  The held:false byte-reupload path was investigated and found not broken — the
  upload route (`POST /v1/evidence/:hash`) only requires the record to exist, and
  `store`/`putStream` overwrite idempotently with no "already stored" refusal
  (covered by the existing held:false→store→held:true test). Regression test in
  `ittreading.test.ts`: filing the same hash against a second project succeeds and

## Feature added — the quality-score floor (submission floor)

A product-owner-confirmed capability, built across **both** submission pipelines
rather than one: the standard tender (Pipeline & Bids) and Bid-On.

- **What it is.** A quality floor — **80% ("4/5") by default, adjustable per
  bid**. In Bid-On, 80 maps to the existing GREEN band threshold; in the
  standard tender it is a proportion of a scored requirement's available marks
  (`scoreBasis.awardedFraction`).
- **Enforcement is a soft block with override-by-reason**, modelled exactly on a
  HIGH red-team finding — *not* a hard block. If a scored quality answer /
  requirement reads below the floor, issuing/exporting is refused and every
  below-floor item is named; a named person can still proceed by recording a
  reason, which is persisted on the record. A genuinely unreachable 4/5 does not
  trap a legitimate bid.
- **Reuse, not a parallel system.** Standard tender raises the breach as a HIGH
  `AssuranceFinding` and the override *is* `disposeFinding` — the existing
  HIGH-override mechanism, nothing new. Bid-On adds `floorOverride` on the answer
  (the mirror of a disposed finding) and extends `packReadiness`/`exportBid`,
  which already refused RED/unapproved answers; the band arithmetic is untouched.
- **Where the floor lives.** `BidResponsePack.qualityFloorPercent` (set at plan,
  `setBidResponseQualityFloor` → `BID_RESPONSE_QUALITY_FLOOR_SET`) and
  `Bid.qualityFloorPercent` (copied at creation like the weights,
  `setBidQualityFloor` → `BID_ON_QUALITY_FLOOR_SET`). The Bid-On per-answer
  override is `overrideQualityFloor` → `BID_ON_ANSWER_FLOOR_OVERRIDDEN`. All
  three events are `aiAllowed: false`: lowering a bar and accepting a below-floor
  answer are human decisions.
- **The rubric/red team surfaces it.** The red-team review stores the floor it
  ran against, names each below-floor requirement, and is refused as stale if the
  floor moves after it ran (the same rule as the pass count). The drafting
  prompts on both sides are given the floor as a stated target so they aim at
  ≥ floor.
- **The honest caveat, stated in code, console and docs.** The gate enforces the
  *findable / rubric* score — the mark the platform's own evaluator can measure
  in the prose — **not the buyer's actual mark**, which no check can guarantee.
  A below-floor finding says the marks are not yet findable, not that the bid
  will score below the floor.
- **Verified** to the full bar: `npm run typecheck` clean, console-lint green,
  the module suites green, and regression tests added in both modules
  (`redteam` "the quality floor" and the new `bidonfloor` suite) covering: a
  below-floor answer blocks and is named; an override-with-reason then clears it;
  a pack at/above the floor issues/exports clean; and a per-bid floor set to a
  different value is respected (including the stale-review refusal when the floor
  moves). **Code + tests verified in this environment; the live site needs a
  redeploy to pick the change up.**
